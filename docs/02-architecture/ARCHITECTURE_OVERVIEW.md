## この環境は何でできているか

Struct Pass のリファレンス実装は、3つの層で構成されています。

```
┌──────────────────────────────────────────────────┐
│                 開発文化                          │
│  ワークフロー・品質基準・AIとの協働ルール          │
│  → AGENTS.md / CONTRIBUTING.md / このドキュメント群 │
├──────────────────────────────────────────────────┤
│                 アプリケーション                   │
│  frontend (Next.js) / backend (NestJS) / shared   │
│  → 業務ロジック・画面・API・型定義                 │
├──────────────────────────────────────────────────┤
│                 インフラ                          │
│  Docker / Caddy / PostgreSQL / GitHub Actions      │
│  → 環境構築・デプロイ・運用                       │
└──────────────────────────────────────────────────┘
```

コードだけを渡すのではなく、**開発文化とインフラを含めた「開発の土台」をまるごと渡す**ことが設計の前提です。

## 設計思想

### 1. 渡せること

すべての設計判断の根底にある原則です。

- **特定クラウドにロックインしない** — AWS EC2 で動いていますが、Docker Compose があればどこでも動きます。AWS 固有のサービス（Lambda, ECS, RDS）には依存していません。
- **OSS のみで構成** — 商用ライセンスが必要なコンポーネントはありません。顧客が自社環境に持ち込む際のライセンス交渉が不要です。
- **環境変数で分離** — `.env.example` をコピーして値を埋めれば、開発・ステージング・本番の切り替えが完了します。コード側の変更は不要です。
- **Markdown + Git で完結** — ドキュメントはすべて Markdown ファイル。特別なツール（Confluence, Notion 等）を前提としません。リポジトリと一緒に渡せます。

### 2. 見通せること

顧客のエンジニアがコードを読んで理解できることを優先しています。

- **モノレポ** — frontend / backend / shared の3パッケージを1つのリポジトリで管理。関連するコードがどこにあるか迷いません。
- **型で繋ぐ** — `packages/shared/` の型定義が frontend と backend の契約になります。API のリクエスト・レスポンスの形は TypeScript の型として明示されています。
- **規約より構造** — NestJS の Module / Controller / Service パターンにより、「この機能のコードはどこにあるか」が構造から自明です。
- **30機能の仕様書** — `docs/03-features/` に全機能の設計仕様があります。コードを読む前に意図を把握できます。

### 3. 壊れにくいこと

引き渡し後に顧客が安心して手を入れられるための設計です。

- **充実したテスト** — バックエンド・フロントエンドあわせて 1,500 件超のユニット/E2E テストを備えます（実数は増加し続けるため概数。正確な件数とカバレッジ閾値の確認方法は `docs/04-development/TESTING_STRATEGY.md` を参照）。
- **監査ログ自動記録** — 全テーブルの CUD 操作を `AuditInterceptor` が自動で記録します。誰が・いつ・何を・どう変えたかが追跡可能です。
- **ロールベースアクセス制御** — 5ロール体系（WH_USER / WH_ADMIN / OF_USER / OF_ADMIN / SYS_ADMIN）で、操作権限がコードレベルで制御されています。
- **セキュリティ監査済み** — Cookie認証、JWT検証、CORS設定、bcryptハッシュ化、入力バリデーションなどを第三者視点で監査し、CRITICAL 4件 + HIGH 7件を修正済みです。

## 構造の意図

### モノレポの3パッケージ

```
packages/
├── frontend/    画面を描く
├── backend/     データを守る
└── shared/      両者の契約（型定義）
```

| パッケージ   | 技術                                 | 責務                                                                                                                                                                                                |
| ------------ | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **frontend** | Next.js 15 + React 19 + Tailwind CSS | ユーザーインターフェース。Server Components でパフォーマンスを確保                                                                                                                                  |
| **backend**  | NestJS + Prisma + PostgreSQL         | ビジネスロジック、認証認可、データ永続化。Controller → Service → Repository → Prisma の4層                                                                                                          |
| **shared**   | TypeScript 型定義のみ                | 主に frontend の共通型置き場。backend は Prisma 生成型と各モジュール内 DTO で型を完結させているが、`FEATURE_IDS` など SSOT 定数は backend からも利用（詳細は [ARCHITECTURE.md](./ARCHITECTURE.md)） |

**なぜこの分け方か**: frontend と backend を完全に分離することで、将来的に別チームが担当する、別のフレームワークに差し替える、といった選択肢を残しています。shared パッケージは主に frontend 内で API レスポンス型を整理する役割を担っており、SSOT 定数（`FEATURE_IDS` など）はバックエンド検証で参照される共有ソースとして機能します。

### バックエンドの層構成

```
リクエスト
  → Guard（認証・認可）
    → Controller（入力の受け取り・レスポンスの返却）
      → Service（ビジネスロジック）
        → Prisma（データベース操作）
  ← Interceptor（監査ログの自動記録）
```

各層の責務が明確に分かれているため、「認可ルールを変えたい」「ビジネスロジックを修正したい」「テーブル構造を変えたい」といった変更が、影響範囲を限定して行えます。

### データ設計の方針

- **全テーブルに監査フィールド** — `created_at`, `updated_at`, `created_by`, `updated_by` を必ず持ちます。
- **論理削除ではなく物理削除 + 監査ログ** — レコードは物理削除しますが、削除前の状態が `audit_logs` に記録されています。
- **Enum で状態管理** — `ReceivingStatus`, `ShipmentStatus`, `OrderStatus` 等、ドメインの状態遷移を PostgreSQL の Enum で表現しています。
- **5ロール体系** — 倉庫系（WH_USER / WH_ADMIN）、事務系（OF_USER / OF_ADMIN）、システム管理者（SYS_ADMIN）。業務の実態に合わせたロール設計です。

## インフラの選択理由

### 本番構成

```
[ブラウザ] → [Caddy (HTTPS/リバースプロキシ)] → [Next.js :3000]
                                                → [NestJS :3001]
                                                → [PostgreSQL :5432]
```

| コンポーネント      | 選定理由                                                                                                           |
| ------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Docker Compose**  | `docker compose up -d` の1コマンドで全サービスが起動。顧客の環境でも同じ手順で再現可能                             |
| **Caddy**           | HTTPS証明書の自動取得・更新。nginx と違い設定ファイルが数行で済む。セキュリティヘッダーも標準装備                  |
| **PostgreSQL 16**   | ACID準拠、Enum型サポート、JSON型サポート。業務システムの堅牢性を担保                                               |
| **EC2 (t4g.small)** | ARM アーキテクチャでコスト効率が良い。特定クラウドサービスに依存しないため、オンプレミスや他クラウドへの移行が容易 |

### 開発構成

```
[ブラウザ] → [Next.js dev :3000] (ホットリロード)
           → [NestJS dev :3001] (ウォッチモード)
           → [PostgreSQL :5432] (Docker)
```

開発時は Docker で PostgreSQL のみを起動し、frontend / backend は `pnpm dev` でホットリロード開発します。本番と開発で PostgreSQL のバージョンが一致するため、環境差異による問題が起きません。
