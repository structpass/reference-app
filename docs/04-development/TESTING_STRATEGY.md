# テスト戦略

> このドキュメントは、多数のユニット/E2E テストの背景にあるテスト設計方針を説明します。テスト件数は日々変わるため、本ドキュメントでは扱いません（下記「現在のテスト構成」で取得方法を示します）。
> テストの実行コマンドは [DEVELOPMENT_GUIDE.md](./DEVELOPMENT_GUIDE.md) とリポジトリの [README](../../README.md#スクリプト)、TDDの原則は [DEVELOPMENT_METHODOLOGY.md](./DEVELOPMENT_METHODOLOGY.md) を参照してください。

---

## テストの目的

テストは「動作確認」ではなく「変更の安全網」です。

顧客がこの環境を引き受けた後、コードを変更するたびに「壊れていないか」を確認できること。これがテストの最大の価値です。

---

## テストピラミッド

```
        ┌───────┐
        │  E2E  │  少数 — クリティカルパスのみ
       ┌┴───────┴┐
       │  統合    │  中程度 — API エンドポイント全体
      ┌┴─────────┴┐
      │  ユニット  │  最多 — Service / Controller / コンポーネント
      └───────────┘
```

下層ほど高速・安定・大量。上層ほど低速・不安定リスクあり・少数。

## 現在のテスト構成

> 件数はモジュール追加のたびに増えるため、本ドキュメントは件数を保管しない。実数は下記コマンドの実行結果で確認する（実数の二重管理を避け drift を防ぐため）。
>
> - バックエンド: `pnpm --filter @struct-pass/backend test`（ユニット）/ `pnpm --filter @struct-pass/backend test:e2e`（E2E、DB 起動が前提）
> - フロントエンド: `pnpm --filter @struct-pass/frontend test`（ユニット）/ `pnpm --filter @struct-pass/frontend test:e2e`（E2E、frontend と rete の起動が前提）

件数を「過去に達成した数」として引用しないでください。テストは増減するため、**現在の全件成功の根拠になるのは、その時点で実行して得た結果**だけです。

### バックエンド（Jest）

| 種別           | 対象                                                                |
| -------------- | ------------------------------------------------------------------- |
| ユニットテスト | Service, Controller, Guard, Interceptor, Filter, Mapper, Repository |
| E2E テスト     | API エンドポイント全体（認証、CRUD、権限検証）                      |

**テストファイルの配置**:

- ユニット: `src/**/*.spec.ts`（テスト対象と同じディレクトリ）
- E2E: `test/**/*.e2e-spec.ts`（プロジェクトルートの test/ ディレクトリ）

### フロントエンド（Vitest）

| 種別           | 対象                                         |
| -------------- | -------------------------------------------- |
| ユニットテスト | コンポーネント, hooks, utils, バリデーション |
| E2E テスト     | クリティカルパスの画面操作（Playwright）     |

**テストファイルの配置**:

- ユニット: `src/__tests__/**/*.test.tsx`（**tests** ディレクトリに集約）
- E2E: `e2e/**/*.spec.ts`（Playwright。ユニットの実行対象とは別）

## カバレッジ方針

### 閾値の正本

閾値の数値はここへ写しません。**各パッケージの設定ファイルを正本**とし、この文書は数値を二重保管しません（写すとランナー更新のたびに片方だけが古くなり、次の読み手が誤った値を信じます）。

| パッケージ | 正本の場所                                                    |
| ---------- | ------------------------------------------------------------- |
| backend    | `packages/backend/package.json` の `jest.coverageThreshold`   |
| frontend   | `packages/frontend/vitest.config.ts` の `coverage.thresholds` |

`shared`（`packages/shared`）には**床を置きません**。DOM を使わない型と定数だけで、試験は「値の形が崩れていないか」を見る錠に近く、率で縛ると分母の作り方だけが問題になります。代わりに `pnpm --filter @struct-pass/shared test` を CI の `test` ジョブで走らせ、試験の型は `pnpm --filter @struct-pass/shared type-check:test` で確かめます（どちらも配線は `scripts/check-ci-wiring.mjs` が照合する）。

CI（`.github/workflows/deploy.yml` の `test` ジョブ）は両パッケージで `test:cov` を実行するため、**設定した床を下回ると CI が失敗します**。床は「目標」ではなく「実測の floor をロックして回帰だけを落とす」ratchet です（frontend の再設定の理由は [ADR 0024](../decisions/0024-vitest4-coverage-reefloor.md)）。したがって指標ごとに値が異なるのが正常で、全指標が同じ値である必要はありません。

### なぜ 80% を目安にするか

80% は**方針の目安**であり、設定に入っている床そのものではありません。床は実測に合わせて指標ごとに置きます。

- **100% は現実的ではない** — 達成コストが急激に上がり、テストの保守負担が増える
- **60% では不十分** — 主要なパスがカバーされず、変更の安全性が担保できない
- **80% はバランス点** — 主要なビジネスロジックとエッジケースをカバーしつつ、過剰なテストを避ける

床を実測へ寄せる時も、この水準は下げません（下げたのは数値であって水準ではない、という判断は ADR 0024）。
計測方法が変わった時は、数値だけでなく**同じものを測った数字か**を先に確かめます。

### カバレッジの4指標

| 指標           | 意味                     | 重視度                             |
| -------------- | ------------------------ | ---------------------------------- |
| **Statements** | 実行された文の割合       | 基本指標                           |
| **Branches**   | if/else 等の分岐カバー率 | 最重要（エッジケースの漏れを検出） |
| **Functions**  | 呼び出された関数の割合   | デッドコード検出に有効             |
| **Lines**      | 実行された行の割合       | Statements と概ね同じ              |

## テストの書き方の方針

### TDD サイクル

```
1. テストを書く（RED）  — 期待する動作を定義
2. テストが失敗することを確認
3. 最小限の実装を書く（GREEN）
4. テストが通ることを確認
5. リファクタリング（IMPROVE）
```

### バックエンドのテストパターン

**Service のユニットテスト**:

- Prisma をモック化し、DB に依存しない
- ビジネスロジック（バリデーション、計算、状態遷移）を検証
- エラーケース（Not Found、権限不足、重複）を網羅

**Controller のユニットテスト**:

- Service をモック化
- リクエストの受け取り・レスポンスの返却を検証
- Guard / Interceptor の適用を確認

**E2E テスト**:

- 実際の DB（テスト用）に接続
- HTTP リクエスト → レスポンスの全体フローを検証
- 認証トークンの取得 → API 呼び出し → レスポンス検証

### フロントエンドのテストパターン

**コンポーネントテスト**:

- レンダリングの確認（必要な要素が表示されるか）
- ユーザー操作のシミュレーション（クリック、入力、送信）
- API モックを使った非同期処理の検証

**hooks テスト**:

- renderHook で独立してテスト
- 状態変更の検証

**バリデーションテスト**:

- Zod スキーマの正常値・異常値を網羅

## テストを変更する場合のガイド

| 状況                 | 方針                                                                              |
| -------------------- | --------------------------------------------------------------------------------- |
| **新機能追加**       | テストを先に書く（TDD）。既存テストは変更しない                                   |
| **バグ修正**         | まず再現テストを書く。テストが RED になることを確認してから修正                   |
| **リファクタリング** | 既存テストを変更しない。テストが GREEN のまま完了すれば、動作が変わっていない証拠 |
| **仕様変更**         | テストを先に修正（新仕様を反映）。テストが RED → 実装を修正 → GREEN               |

### テストを消してはいけない場合

- カバレッジを上げるために別のテストに書き換える場合以外
- 「テストが邪魔だから」という理由で消すのは禁止

### テストを消してよい場合

- テスト対象の機能自体が削除された場合
- 重複するテスト（同じ動作を複数のテストで検証している場合）の整理

## テスト実行コマンド

```bash
# バックエンド
pnpm --filter @struct-pass/backend test          # ユニットテスト
pnpm --filter @struct-pass/backend test:cov      # カバレッジ付き
pnpm --filter @struct-pass/backend test:e2e      # E2E テスト

# フロントエンド
pnpm --filter @struct-pass/frontend test         # ユニットテスト
pnpm --filter @struct-pass/frontend test:cov     # カバレッジ付き

# 全パッケージ
pnpm test                                        # 全ユニットテスト
pnpm test:cov                                    # 全カバレッジ
```
